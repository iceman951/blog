เคยสงสัยไหมว่าทำไม ElysiaJS ถึงเร็ว? หลายคนอาจนึกถึง Bun ก่อน แต่ทุกครั้งที่มีคนเรียก API ยังมีงานอีกหลายขั้นก่อนแอปจะตอบกลับ ถ้าบางขั้นไม่จำเป็นสำหรับคำขอนั้น เราข้ามมันได้ไหม?

## ศัพท์ที่ใช้ในบทความนี้

| คำ | หมายถึงอะไรในบทความนี้ |
| --- | --- |
| **Runtime / framework** | Runtime คือสภาพแวดล้อมที่รัน JavaScript เช่น Bun หรือ Node.js ส่วน framework คือเครื่องมือที่จัดการ route และ request เช่น Elysia หรือ Express |
| **Request / response** | Request คือคำขอที่ผู้ใช้หรือโปรแกรมอื่นส่งเข้า API; response คือคำตอบที่ API ส่งกลับ |
| **Route / handler** | Route คือคู่ของ HTTP method กับ path เช่น `GET /user`; handler คือฟังก์ชันที่เขียนไว้ให้ทำงานเมื่อ request ตรง route นั้น |
| **Middleware / hook** | ฟังก์ชันที่ทำงานระหว่างขั้นตอนรับ request กับส่ง response เช่น ตรวจสิทธิ์หรือบันทึก log; Express มักเรียก middleware ส่วน Elysia มี lifecycle hooks |
| **Query / body / headers / cookies** | ข้อมูลคนละส่วนของ request: query อยู่หลัง `?` ใน URL, body เป็นข้อมูลที่ส่งมาพร้อมคำขอ, headers เป็นข้อมูลกำกับ และ cookies เป็นค่าที่ส่งผ่าน header |
| **Parse** | อ่านและแปลงข้อมูลดิบจาก request ให้อยู่ในรูปที่โค้ดใช้ได้ เช่นแปลง `?id=42` เป็นค่า `query.id` |
| **Static Analysis / Code Generation** | อย่างแรกคืออ่านโค้ดเพื่อดูว่าต้องใช้อะไรโดยไม่เรียก handler; อย่างหลังคือนำผลนั้นมาสร้าง JavaScript สำหรับจัดการ route |
| **JIT / AOT** | JIT คือเตรียมหรือปรับโค้ดระหว่างที่โปรแกรมทำงาน; AOT คือเตรียมก่อนช่วงที่จะใช้โค้ดนั้น บทความจะระบุต่อว่า *ใคร* เป็นคนเตรียมและทำ *เมื่อไร* |

คำตอบสั้น ๆ คือ Elysia พยายามรู้ความต้องการของแต่ละ route ล่วงหน้า แล้วสร้าง request handler ที่ทำงานเท่าที่ route นั้นต้องใช้ [Abstract ของงานวิจัย Elysia ใน ACM SAC 2024](https://doi.org/10.1145/3605098.3636068) วางโจทย์ทั้งความเร็ว ความสะดวกในการพัฒนา และ type safety โดยเสนอ Static Analysis กับ Dynamic Code Generation เพื่อลดต้นทุนขณะรันของฟีเจอร์ที่ช่วยให้เขียนโค้ดสะดวก บทความนี้อ้างแนวคิดจาก abstract; รายละเอียดการทำงานของ framework อิง[เอกสาร internals ของ Elysia](https://elysiajs.com/internal/jit-compiler) เพราะ implementation เปลี่ยนได้หลัง paper เผยแพร่

เพื่อให้เห็นความต่าง ผมจะใช้ **Express 5 เป็นตัวเทียบตลอดบทความ** โดยดูว่า route แบบเดียวกันจัดการ request อย่างไร ไม่ใช่นำตัวเลขความเร็วของสอง framework มาแข่งกัน

## หนึ่ง request: framework ต้องเตรียมอะไรให้ handler?

ลองดู route ที่รับ `/user?id=42` แล้วคืนค่า `id` จาก query string หรือส่วนหลังเครื่องหมาย `?` ใน URL:

```ts
app.get('/user', ({ query }) => query.id)
```

handler นี้ใช้ `query` แต่ไม่ได้อ่าน body, headers หรือ cookies ถ้าไม่มี hooks หรือ schema เพิ่มเติม งานที่ต้องทำก่อนเรียก handler จึงต่างจาก route ที่รับ JSON body หรืออ่าน cookie เพื่อยืนยันตัวตน

ใน Express 5 เราเขียน route เดียวกันได้แบบนี้:

```js
app.get('/user', (req, res) => {
  res.send(String(req.query.id))
})
```

Express จับคู่ path และ method แล้วเรียก callback ที่ลงทะเบียนไว้ `req.query` จะถูกอ่านใน callback นี้ ส่วนการ parse body ต้องเพิ่ม middleware เช่น `express.json()` เอง ตาม[เอกสาร middleware ของ Express](https://expressjs.com/en/guide/using-middleware/) ดังนั้น Express ตัวอย่างนี้ก็ไม่ได้ parse body หรือ cookies โดยอัตโนมัติ

ภาพฝั่ง “เตรียมทุกส่วน” เป็นตัวอย่างให้เห็นต้นทุน **ไม่ใช่ภาพการทำงานของ Express 5** ซึ่งใช้ `req.query` แบบ getter และแปลง query เมื่อมีการอ่านค่านั้น ตาม[เอกสาร Express 5](https://expressjs.com/en/guide/migrating-5/) และ[source ของ `req.query`](https://github.com/expressjs/express/blob/master/lib/request.js) ในภาพ การไม่เตรียม headers หมายถึงไม่อ่านหรือแปลง headers เพื่อใส่ context ของ handler เมื่อ route ไม่ใช้ ไม่ได้หมายความว่า HTTP request ไม่มี headers จุดสำคัญคือการอ่านและแปลงข้อมูลที่ไม่ได้ใช้ก็มีค่าใช้จ่าย แม้งานแต่ละครั้งจะเล็ก แต่จะเกิดซ้ำทุก request

อีกด้านหนึ่ง การข้ามงานต้องไม่เปลี่ยนพฤติกรรมของแอป ถ้า hook ต้องอ่าน headers หรือ schema ต้องตรวจ body ข้อมูลเหล่านั้นก็ยังต้องถูกเตรียมและตรวจตามปกติ ตัวอย่างนี้จงใจให้ route ไม่มีเงื่อนไขอื่น เพื่อให้เห็นหลักการก่อน

## Static Analysis: Elysia รู้ได้อย่างไรว่า route ใช้อะไร?

ตัววิเคราะห์ของ Elysia ชื่อ **Sucrose** มันอ่านโค้ดของ handler โดยไม่เรียก handler ให้ทำงาน ใช้ `Function.toString()` ร่วมกับ pattern matching เพื่อดูว่า handler ต้องใช้ข้อมูลส่วนไหนของ request จากตัวอย่างข้างบน สิ่งที่ต้องเตรียมคือ `query`

คำว่า *Static Analysis* ในที่นี้หมายถึงการดูโค้ดเพื่อหาข้อมูลก่อนนำ handler ไปตอบ request ไม่ได้หมายความว่าต้องเกิดตอน build และ Sucrose ก็ไม่ได้ทำหน้าที่แทน TypeScript compiler ที่ตรวจชนิดข้อมูลทั้งโปรเจกต์

ผลการวิเคราะห์เป็นข้อมูลให้ขั้นตอนถัดไปเลือกว่าจะประกอบ request handler อย่างไร โดยต้องนับความต้องการของ hooks และ schema ด้วย ไม่ใช่ดูแค่บรรทัด `return` ของเรา

**เทียบกับ Express 5:** เราเลือกเองว่าจะลงทะเบียน middleware แบบครอบทุก request ด้วย `app.use()` หรือเฉพาะ path/route ที่ต้องใช้ Express จะรัน middleware ที่เข้ากับ request ตามลำดับที่ลงทะเบียน ส่วน Elysia เพิ่มอีกขั้นด้วยการอ่าน handler เพื่อหาว่าข้อมูลใดควรอยู่ในเส้นทางของ route นั้น การวาง middleware ให้แคบใน Express จึงเป็นงานออกแบบของคนเขียนแอป ไม่ใช่ผลของ Sucrose

## Code Generation: ผลวิเคราะห์กลายเป็น handler อย่างไร?

เมื่อรู้ว่า route ต้องใช้อะไร Elysia สามารถสร้าง JavaScript สำหรับจัดการ route นั้นโดยเฉพาะ แทนการให้ทุก route ผ่านฟังก์ชันทั่วไปที่ตัดสินใจเรื่องเดิมซ้ำ ๆ ทุก request ภาพย่อของโค้ดที่ได้อาจหน้าตาแบบนี้:

```js
function tailoredHandler(request) {
  const context = {
    request,
    query: parseQuery(request.url)
  }

  return mapResponse(routeHandler(context))
}
```

**โค้ดนี้เป็นภาพจำลอง ไม่ใช่ source code ของ Elysia** ชื่อ `parseQuery`, `mapResponse` และ `routeHandler` ใช้แทนขั้นตอนจริง และละ validation, hooks กับ error handling ไว้ ตัวอย่างแสดงเพียงว่า handler ที่รู้ว่าต้องใช้ `query` สามารถมีขั้นตอนเตรียม `query` โดยไม่ใส่งานที่ route ไม่ต้องใช้

<ElysiaFlowDiagram kind="handler" />

ใน[เอกสาร internals ของ Elysia 1.x](https://elysiajs.com/internal/jit-compiler) ส่วนที่สร้างโค้ดนี้เรียกว่า JIT “compiler” และใช้ `new Function(...)` เอกสารอธิบายว่า handler จะถูกสร้างเมื่อ request แรกเรียก route นั้น จากนั้น request ถัดไปใช้ handler ที่เตรียมไว้ งานอย่างการ parse `query` ยังต้องทำกับ request ใหม่ทุกครั้ง แต่ไม่ต้องสร้าง handler ของ route ใหม่ทุกครั้ง

**เทียบกับ Express 5:** request วิ่งผ่าน middleware ที่ตรงเงื่อนไข แล้ว Express เรียก callback ของ route และ `res.send()` ตามที่เราเขียน ไม่มีขั้นสร้าง JavaScript สำหรับ route นี้จากการอ่าน source ของ callback แบบ Elysia แต่ Express ก็ข้ามงานที่เราไม่ได้ลงทะเบียนไว้ได้ เช่น route ตัวอย่างที่ไม่มี body parser ประเด็นที่ต่างกันจึงอยู่ที่ *วิธีตัดสินใจและประกอบงาน* ไม่ใช่ว่า Express ต้องเตรียมข้อมูลทุกชนิด

## AOT กับ JIT: งานสร้าง handler เกิดตอนไหน?

คำว่า “compile” ตรงนี้มี **สองชั้น** จึงสับสนได้ง่าย:

| ใครทำ | ทำอะไร |
| --- | --- |
| Elysia | วิเคราะห์ route แล้วสร้าง JavaScript สำหรับ request handler |
| JavaScript engine | นำ JavaScript ที่ได้ไปรัน และอาจ optimize หรือ JIT โค้ดระหว่างรัน |

**JIT (Just-in-Time)** คือการเตรียมหรือ optimize โค้ดขณะโปรแกรมกำลังทำงาน เมื่อเอกสาร Elysia พูดถึง JIT “compiler” กำลังพูดถึงชั้นแรก ไม่ใช่ JIT ภายใน engine ส่วน **AOT (Ahead-of-Time)** หมายถึงย้ายงานเตรียมโค้ดไปก่อนช่วงที่จะใช้งาน แต่ต้องถามต่อว่า “ก่อน” ในขั้นตอนไหน

| วิธีเตรียม handler | งานของ Elysia เกิดเมื่อไร | สิ่งที่แลกเปลี่ยน |
| --- | --- | --- |
| Elysia 1.x แบบ lazy ตาม[เอกสาร internals](https://elysiajs.com/internal/jit-compiler) | request แรกของ route | เริ่มแอปได้โดยยังไม่เตรียมทุก route แต่ request แรกจ่ายต้นทุนนี้ |
| Elysia 1.x ตั้ง [`precompile: true`](https://elysiajs.com/patterns/configuration#precompile) | ตอนเริ่มแอป | ย้ายต้นทุนจาก request แรกไป startup |
| Elysia 2 beta แบบไม่ใช้ build plugin ตาม[ประกาศรุ่น](https://elysiajs.com/blog/elysia-20) | ตอนเริ่มแอป | เตรียม handler ของแต่ละ route ก่อนรับ request |
| Elysia 2 beta ใช้ [AOT build plugin](https://elysiajs.com/blog/elysia-20) | ตอน build | ย้ายงานสร้าง handler ไปก่อนเริ่มแอป ต้องตั้งค่า build เพิ่ม |

ณ วันที่ตรวจ **30 กันยายน 2026** Elysia 2 ยังเป็น beta ผ่าน `elysia@next` ตารางนี้จึงเทียบคำอธิบายของแต่ละรุ่น ไม่ใช่ตัวเลือกทั้งหมดในรุ่นเดียว ทั้งสี่กรณีต่างกันที่จังหวะจ่ายต้นทุนการเตรียม ส่วน JavaScript engine ยังจัดการโค้ดอีกชั้นขณะรัน

**เทียบกับ Express 5:** ตารางนี้แสดงช่วงที่ Elysia สร้าง handler ในแต่ละรุ่น ไม่ใช่โหมดที่ต้องเลือกใน Express เมื่อ Express เรียก callback ที่ลงทะเบียนไว้ JavaScript engine ของ runtime ก็ยังอาจ JIT หรือ optimize callback นั้นได้เหมือนกัน ดังนั้น “Elysia มี JIT compiler” ไม่ได้แปลว่า “Express ไม่มี JIT เลย”

## Bun ช่วยตรงไหน และ Elysia ช่วยตรงไหน?

Bun เป็น runtime ที่ให้ HTTP server และ API สำหรับจัดการ request ส่วน Elysia เลือกว่าต้องทำขั้นตอนไหนก่อนเรียก handler สองส่วนนี้จึงช่วยกันได้: Elysia ลดขั้นตอนที่ไม่จำเป็นต่อ route และยังใช้ความสามารถเฉพาะของ Bun เมื่อเหมาะสม เช่น `Bun.serve.routes` สำหรับ routing หรือ `Bun.file` สำหรับไฟล์ ตาม[เอกสาร platform-specific optimization](https://elysiajs.com/internal/jit-compiler#platform-specific-optimization)

ดังนั้นคำตอบของ “Elysia เร็วเพราะ Bun อย่างเดียวไหม?” คือ **ไม่ใช่อย่างเดียว** แต่ก็แยกผลของ Bun ออกจากผลของ framework ด้วยการดูตัวเลข throughput ตัวเดียวไม่ได้ ต้องทดสอบภายใต้ runtime และ workload เดียวกัน

**เทียบกับ Express 5:** Express ก็[รันบน Bun ได้](https://bun.sh/guides/ecosystem/express) ผ่าน API ที่เข้ากันได้กับ Node.js ถ้าเอา Elysia บน Bun ไปเทียบกับ Express บน Node.js ผลจะรวมความต่างของ runtime เข้าไปด้วย การรันทั้งคู่บน Bun ช่วยให้คำถามเรื่อง framework ชัดขึ้น แม้เส้นทาง HTTP ภายในและ middleware ที่ใช้ยังต้องดูให้ตรงกัน

## Benchmark บอกอะไร และควรใช้ตัดสินใจอย่างไร?

[Abstract ของ paper](https://doi.org/10.1145/3605098.3636068) ระบุว่าผู้วิจัยประเมิน Elysia เทียบกับโค้ดที่ยังไม่ optimize และ backend framework อื่น แต่ abstract ไม่แจกแจงว่ากลไกแต่ละตัวลดเวลาลงเท่าไร บทความนี้จึงไม่ดึงตัวเลขเฉพาะส่วนจาก paper มาฟันธงผลของแต่ละเทคนิค

เวลาอ่าน benchmark ควรแยก **microbenchmark** ที่วัดขั้นตอนเล็ก ๆ ออกจาก **HTTP benchmark** ที่วัดทั้งเส้นทางรับส่ง request ตัวเลข operations/second ของการเรียกฟังก์ชันไม่ใช่ requests/second ของ API และทั้งคู่ยังไม่บอกโดยตรงว่าแอปที่คุยกับฐานข้อมูลจะเร็วขึ้นเท่าไร

ถ้าจะเทียบ Elysia กับ Express ให้เริ่มจาก route ที่ตอบข้อมูลเดียวกันบน runtime เดียวกัน แล้วระบุ middleware, validation และวิธีส่ง response ให้ครบ ตัวเลขที่ได้บอกผลของ *ทั้งเส้นทาง* ในเงื่อนไขนั้น ไม่ได้พิสูจน์ว่า Static Analysis เพียงตัวเดียวทำให้ต่างกันเท่าไร

ถ้า route ตอบข้อมูลที่อยู่ในหน่วยความจำและทำงานน้อย overhead ของ framework อาจเป็นสัดส่วนใหญ่ การลดงานต่อ request จึงเห็นผลได้ชัดขึ้น แต่ถ้าเวลาส่วนใหญ่หมดไปกับ database หรือ network การลดงานของ framework จะเปลี่ยนเวลารวมได้น้อยกว่า ตัวอย่างจาก[การทดสอบ Elysia กับ Hono บน PostgreSQL ของผม](/blog/th/elysia-hono-postgres-on-m5-air/) แสดงเหตุผลที่ควรวัดกับงานใกล้เคียงแอปจริงก่อนเลือก framework จากอันดับ benchmark

สรุปคือ Express ให้เราเลือก middleware และเข้าถึงข้อมูลจาก request เมื่อใช้ ส่วน Elysia เพิ่มการวิเคราะห์ route แล้วสร้าง handler ให้ทำงานพอดีกับข้อมูลที่ต้องใช้ Bun ช่วยให้ขั้นตอนที่เหลือทำงานได้เร็ว แต่ถ้าอยากรู้ว่าแอปของเราเร็วขึ้นแค่ไหน ต้องวัดว่าเวลาในแอปหมดอยู่ที่ framework จริงหรือเปล่า
