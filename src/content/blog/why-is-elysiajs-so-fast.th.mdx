เคยสงสัยกันไหมครับว่าทำไม ElysiaJS ถึงเร็ว?

ก่อนจะหาคำตอบ ลองมาดูกันว่า framework อย่าง Express หรือ Fastify จัดการ request อย่างไร แล้วค่อยดูว่า ElysiaJS ทำอะไรต่างออกไปบ้าง

รายละเอียด implementation ด้านล่างอ้างอิง **Elysia 1.4.30** โดยลิงก์ source code ระบุ version ไว้เพื่อให้ตรวจย้อนกลับได้ โค้ดใน version ใหม่อาจต่างจากที่อธิบาย ส่วน build-time AOT แยกอ้างอิงกับ [Elysia 2 beta](https://elysiajs.com/blog/elysia-20#ahead-of-time-compilation) เพื่อไม่ปะปนกันระหว่าง version

## Framework จัดการ request อย่างไร?

นอกจากจับคู่ HTTP method และ path แล้ว framework ยังจัดการขั้นตอนอื่น ๆ ทั้งก่อนและหลังเรียก handler เช่น parsing, validation, hooks, error handling และการแปลงค่าที่คืนมาเป็น HTTP response แต่ละ request จึงต้องใช้เวลาและทรัพยากรกับขั้นตอนเหล่านี้ด้วย แม้ business logic จะมีแค่ไม่กี่บรรทัด

แต่ละ framework จัดลำดับงานต่างกัน ลองดูภาพด้านล่าง: Express เรียก middleware ตามลำดับที่เราลงทะเบียนไว้ ส่วน Fastify มีขั้นตอนหลักกำหนดไว้แล้ว และให้เราเพิ่มโค้ดผ่าน hooks ในแต่ละช่วง

<FrameworkLifecycleDiagram />

งานส่วนหนึ่งคือการเตรียมข้อมูลให้ handler เช่น parse query string, decode JSON body หรือแปลง headers เป็น object ใน context แต่ละขั้นตอนใช้เวลาและทรัพยากรต่างกัน เช่น การอ่าน headers ที่ HTTP server เตรียมไว้แล้ว กับการ parse body เพื่อแปลงข้อมูลให้อยู่ในรูปที่ handler ใช้งานได้

ลองสมมติว่าหลังเลือก route แล้ว เรามีฟังก์ชันกลางที่เตรียมข้อมูลทุกส่วนก่อนเรียก handler โค้ดต่อไปนี้เป็นแบบจำลองเพื่อเทียบแนวคิด ไม่ใช่ implementation ของ Express หรือ Fastify:

```js
async function centralHandler(request) {
  const context = {
    request,
    body: await parseBody(request),
    query: parseQuery(request.url),
    headers: prepareHeaders(request.headers),
    cookie: parseCookies(request.headers.get('cookie'))
  }

  return mapResponse(await routeHandler(context))
}
```

ชื่อฟังก์ชันในตัวอย่างแทนงานแต่ละขั้น โดยสมมติว่า `parseBody` รองรับ request ที่ไม่มี body และ `mapResponse` แปลงผลจาก handler เป็น response ส่วน routing, validation และ error handling ละไว้เพื่อให้เห็นเฉพาะงานเตรียม context

ถ้า handler อ่านแค่ `query.id` ฟังก์ชันกลางนี้ก็ยังเรียกขั้นตอนเตรียม body, headers และ cookies ทุกครั้ง การตัดงานที่ไม่จำเป็นออกจึงมีโอกาสลดทั้ง CPU time และการสร้าง object ต่อ request

framework จริงมีวิธีหลีกเลี่ยงงานเหล่านี้อยู่แล้ว เช่น เลือก middleware เฉพาะ route หรือ parse เมื่อมีการอ่านค่า เราจะกลับมาเทียบกับ Express 5 หลังจากเห็นกลไกของ Elysia

แนวทางของ Elysia คือใช้ข้อมูลของ route มาตัดสินใจก่อนว่า request pipeline ต้องมีขั้นตอนไหนบ้าง

## ElysiaJS ทำต่างออกไปอย่างไร?

ในโหมดที่เปิด code generation Elysia วิเคราะห์ handler และ hooks แล้วใช้ผลร่วมกับ schema, HTTP method และ adapter เพื่อประกอบ request pipeline ของ route นั้น เงื่อนไขเลือกงานเหล่านี้อยู่ใน [`compose.ts` ของ version 1.4.30](https://github.com/elysiajs/elysia/blob/1.4.30/src/compose.ts)

สมมติว่าเรามี API ที่รับ `/user?id=42` แล้วตอบกลับด้วยค่า `id`:

```ts
import { Elysia } from 'elysia'

const app = new Elysia()
  .get('/user', ({ query }) => query.id)
```

สำหรับ `/user?id=42` ตัวอย่างนี้คืนค่า `'42'` เป็น string เพราะไม่ได้กำหนด schema ให้แปลง `id` เป็นตัวเลข โค้ดนี้แสดงเฉพาะการอ่านค่าจาก query เพื่อให้เข้าใจขั้นตอนการทำงานได้ง่าย ส่วน API ที่นำไปใช้งานจริงควรกำหนด validation และระบุให้ชัดเจนว่าจะจัดการอย่างไรเมื่อไม่มี `id`

เมื่อไม่มี hooks หรือ schema ที่ต้องใช้ headers หรือ cookies เพิ่มเติม route นี้ก็ไม่จำเป็นต้องเตรียมข้อมูลเหล่านั้นใน context ส่วนการ parse body ยังขึ้นอยู่กับ HTTP method ด้วย โดย Elysia version ที่อ้างอิงจะไม่สร้างขั้นตอน parse body สำหรับ `GET` และ `HEAD` อยู่แล้ว การข้ามขั้นตอนนี้ในตัวอย่างจึงไม่ได้เป็นผลจาก static analysis เพียงอย่างเดียว

ภาพนี้เปรียบเทียบฟังก์ชันที่ทำทุกขั้นตอนกับ pipeline ที่เลือกทำเฉพาะขั้นตอนที่แต่ละ route ต้องใช้ ช่วยให้เห็นว่าข้ามขั้นตอนไหนได้บ้าง แต่ไม่ได้บอกว่าเร็วขึ้นกี่เท่า

แล้ว Elysia รู้ได้อย่างไรว่า handler ต้องใช้อะไร?

## Sucrose: อ่านโค้ดก่อนเรียกใช้งาน

**Sucrose คือตัวช่วยของ Elysia ที่อ่านโค้ดฟังก์ชัน แล้วจดว่า “ฟังก์ชันนี้ต้องใช้ข้อมูลส่วนไหนบ้าง”** เพื่อให้ Elysia เลือกเตรียมข้อมูลให้เหมาะกับ route นั้นครับ

ลองกลับมาดู route เดิม:

```ts
app.get('/user', ({ query }) => query.id)
```

ฟังก์ชัน `({ query }) => query.id` คือ **handler** ส่วน **context** คือ object ที่ Elysia ส่งให้ handler ใช้จัดการ request ในตัวอย่างนี้เราใช้ `{ query }` ดึงเฉพาะข้อมูล query ออกมาจาก context

เมื่อ request `/user?id=42` เข้ามา Elysia ต้องแปลงข้อความ `id=42` ใน URL ให้เป็นข้อมูลประมาณ `{ id: '42' }` ก่อน handler จึงจะอ่าน `query.id` ได้ แต่ Elysia จะรู้ได้อย่างไรว่าต้องเตรียม query? ตรงนี้คือหน้าที่ของ Sucrose

**ขั้นแรก: เปลี่ยนฟังก์ชันเป็นข้อความ แล้วอ่านรูปแบบโค้ด**

JavaScript สามารถเรียก `toString()` บนฟังก์ชันได้ ลองแยก handler ออกมาให้เห็นชัด ๆ:

```js
const handler = ({ query }) => query.id

handler.toString()
// ได้ข้อความประมาณ "({ query }) => query.id"
```

Sucrose ตรวจข้อความนี้แล้วพบว่า parameter ดึง `query` ออกมาใช้ จึงบันทึกผลประมาณนี้ โดยย่อเฉพาะบางช่อง:

```js
{
  query: true,
  body: false,
  headers: false,
  cookie: false
}
```

`true` หมายถึงพบการใช้ข้อมูลส่วนนั้น ส่วน `false` หมายถึงยังไม่พบจากการวิเคราะห์นี้ Sucrose จึงบอกได้ว่า “ต้องใช้ query” โดยยังไม่ต้องเรียก handler และยังไม่ต้องรู้ว่า request จริงจะส่ง `id` เป็นค่าอะไร ดูกลไกได้ใน [`sucrose.ts`](https://github.com/elysiajs/elysia/blob/1.4.30/src/sucrose.ts#L616-L719)

ผลนี้ระบุการใช้ `query` ทั้งส่วน ไม่ได้บอกว่าจะ parse เฉพาะ key `id` เสมอไป

**ขั้นต่อมา: นำผลวิเคราะห์ไปเลือกงานที่ต้องทำ**

Elysia มีอีกส่วนที่ทำหน้าที่ประกอบ **pipeline** หรือ “ลำดับขั้นตอนจัดการ request” ส่วนนี้นำผลจาก Sucrose มาใช้ร่วมกับข้อมูลอื่น เช่น schema และ HTTP method เพื่อตัดสินใจว่าจะใส่ขั้นตอนเตรียมข้อมูลอะไรบ้าง ตามโค้ดใน [`compose.ts`](https://github.com/elysiajs/elysia/blob/1.4.30/src/compose.ts#L508-L540)

สำหรับตัวอย่างนี้ ถ้าไม่มี hooks หรือ schema ที่ต้องใช้ headers และ cookies เพิ่มเติม pipeline ก็ไม่จำเป็นต้องมีขั้นตอนเตรียมข้อมูลสองส่วนนี้ใน context งานที่ลดลงตรงนี้ช่วยลดต้นทุนต่อ request

เราจึงแยกหน้าที่แต่ละส่วนได้แบบนี้:

- **Sucrose:** อ่านโค้ดแล้วบอกว่า “พบการใช้ query”
- **ตัวประกอบ pipeline:** ตัดสินใจว่า “ต้องใส่ขั้นตอนเตรียม query”
- **เมื่อจัดการ request จริง:** pipeline เตรียม query จาก URL ของ request นั้น แล้วเรียก handler

Sucrose ยังอ่านโค้ดของ **hooks** ซึ่งเป็นฟังก์ชันที่เราให้ Elysia เรียกในช่วงต่าง ๆ ของการจัดการ request ด้วย เช่น ถ้ามี `beforeHandle` ที่อ่าน `headers.authorization` เพื่อตรวจสิทธิ์ ผลวิเคราะห์รวมก็ต้องระบุว่าใช้ headers แม้ handler หลักจะอ่านแค่ query ส่วน schema หรือข้อกำหนดรูปแบบข้อมูล ก็เป็นอีกเหตุผลที่ pipeline อาจต้องเตรียมข้อมูลมาตรวจสอบ

**แล้วถ้าโค้ดไม่ได้บอกชัด ๆ ว่าใช้ข้อมูลอะไร?**

ลองเทียบสองแบบนี้:

```ts
// เห็นชัดว่า handler ใช้ query แล้วส่งค่า id ต่อไป
({ query }) => service(query.id)

// ส่ง context ทั้งก้อนไปให้ service
context => service(context)
```

แบบหลัง `service` อาจอ่าน body, headers หรือ cookie ข้างในอีกที เมื่อ Sucrose ตรวจพบการส่ง context ทั้งก้อนแบบนี้ มันจะเผื่อว่าฟังก์ชันปลายทางอาจใช้ข้อมูลทุกส่วนที่มันติดตาม จึงมีโอกาสตัดขั้นตอนเตรียมข้อมูลออกได้น้อยลง ดู[โค้ดตรวจการส่ง context ต่อ](https://github.com/elysiajs/elysia/blob/1.4.30/src/sucrose.ts#L516-L547)

วิธีอ่านรูปแบบโค้ดโดยไม่เรียกฟังก์ชันนี้เรียกว่า **static analysis** โดย Sucrose ทำงานเฉพาะด้านการตรวจว่ามีการใช้ข้อมูลอะไรบ้าง ไม่ได้อาศัย type information ของ TypeScript และไม่ได้เข้าใจ JavaScript ครบทุกกรณี การเขียนให้เห็นชัดว่าใช้ข้อมูลส่วนไหนจึงช่วยทั้งคนอ่านและตัววิเคราะห์

คำว่า “static” ตรงนี้อธิบาย **วิธีวิเคราะห์** ส่วน **วิเคราะห์เมื่อไร** เป็นอีกเรื่องหนึ่ง อาจเกิดระหว่างเตรียมแอปหรือเมื่อเรียก route ครั้งแรก ขึ้นอยู่กับ version และโหมดที่ใช้ เราจะดูเรื่องจังหวะนี้ต่อในหัวข้อ JIT กับ AOT

## จากผลวิเคราะห์ สู่ handler เฉพาะ route

เมื่อรู้แล้วว่า route ต้องใช้ข้อมูลอะไร Elysia ก็นำผลวิเคราะห์มารวมกับการตั้งค่าของ route แล้วสร้างฟังก์ชันที่เตรียมข้อมูลและเรียก handler ของเรา สำหรับตัวอย่างที่ handler คืนค่าได้ทันทีโดยไม่ต้อง `await` แนวคิดของโค้ดที่สร้างขึ้นเป็นแบบนี้:

```js
function tailoredHandler(request) {
  const context = {
    request,
    query: parseQuery(request.url)
  }

  return mapResponse(routeHandler(context))
}
```

นี่เป็น pseudocode ไม่ใช่โค้ดที่ dump ออกมาจาก Elysia จริง ตัวอย่างละ hooks, validation, error handling และการรองรับ async handler ไว้

สิ่งที่สร้างขึ้นคือฟังก์ชันครอบ handler ของเราอีกชั้น โดยเลือกใส่เฉพาะขั้นตอนที่ pipeline นี้ต้องใช้ เมื่อประกอบแล้ว request ถัดไปก็เรียกฟังก์ชันนั้นซ้ำได้

<ElysiaFlowDiagram kind="handler" />

**สิ่งที่นำกลับมาใช้คือโค้ดของ pipeline** ส่วน context และข้อมูล query ยังมาจาก request ปัจจุบัน เช่น `/user?id=43` ก็ต้องคืน `'43'` กลไกนี้จึงแยกจาก response caching

นี่คือ **code generation**: นำการตัดสินใจที่อาศัยข้อมูลคงที่ของ route ไปทำตอนประกอบโค้ด เช่น route มี schema หรือ hooks ใดบ้าง ส่วนเงื่อนไขที่ขึ้นกับ request จริง เช่นข้อมูลผ่าน validation หรือไม่ ยังต้องตรวจทุกครั้ง

## JIT กับ AOT ต่างกันที่จังหวะเตรียมโค้ด

[บทความ internals ของ Elysia](https://elysiajs.com/internal/jit-compiler) เรียกกลไกนี้ว่า **JIT (Just-in-Time) “compiler”** โดยใช้ `Function` constructor สร้างฟังก์ชันจากข้อความ JavaScript ระหว่างที่แอปทำงาน ในเส้นทางแบบ lazy งานประกอบ pipeline จะเกิดเมื่อ route ถูกเรียกครั้งแรก

จุดที่ชวนสับสนคือ Elysia 1.x ใช้ชื่อ option ว่า `aot` สำหรับเปิดเส้นทาง code generation นี้ด้วย ดังนั้น **`aot: true` ไม่ได้แปลว่ามีการสร้างไฟล์ไว้ตอน build** ส่วน `precompile` ใช้ควบคุมว่าจะประกอบ route ล่วงหน้าหรือรอจนมีการเรียก ดูการแยกสอง option นี้ใน [`index.ts` ของ version 1.4.30](https://github.com/elysiajs/elysia/blob/1.4.30/src/index.ts)

| วิธีเตรียม handler | สร้างเมื่อไร | ผลที่ได้ |
| --- | --- | --- |
| Elysia 1.4.30 เปิด `aot` และใช้เส้นทาง lazy | เมื่อเรียก route ครั้งแรก | เลื่อนงานประกอบ route ไปจนกว่าจะใช้งาน |
| Elysia 1.4.30 เปิด `aot` และ `precompile: true` | ระหว่างเตรียมแอป ก่อนเริ่มรับ request | ลดงานประกอบ route ใน request แรก โดยเพิ่มงานช่วง startup |
| Elysia 2 beta ใช้ AOT build plugin ตามประกาศ | ตอน build | เตรียมโค้ดของ handler และ schema ที่ plugin รองรับไว้ใน build output |

ตารางนี้แยก **การเตรียมล่วงหน้าภายใน process** ออกจาก **build-time AOT** รายละเอียดอ้างอิง [`precompile`](https://elysiajs.com/patterns/configuration#precompile) และ [ blog Elysia 2 beta](https://elysiajs.com/blog/elysia-20#ahead-of-time-compilation) ไม่ได้หมายความว่าทุก route หรือ adapter ใช้เส้นทางเดียวกัน เช่น static response อาจมีเส้นทางเฉพาะของ runtime

อีกชั้นหนึ่งคือ **JIT ของ JavaScript engine** ซึ่งสามารถ compile และ optimize JavaScript เป็น machine code ระหว่างรัน ส่วน code generation ของ Elysia ให้ผลเป็น JavaScript ของ request pipeline การเปิด `precompile` จึงไม่ได้รับประกันว่า engine ทำ warm-up เสร็จแล้ว

## แล้ว Bun ช่วยตรงไหน?

Bun ให้ทั้ง JavaScript runtime และ HTTP server ผ่าน `Bun.serve()` โดยใช้ JavaScriptCore เป็น engine ส่วน Elysia จัดการ routing และ request lifecycle บนความสามารถเหล่านั้น ตาม[เอกสาร runtime](https://bun.sh/docs/runtime) และ[HTTP server ของ Bun](https://bun.sh/docs/runtime/http/server)

ประสิทธิภาพที่วัดได้จึงมาจากหลายชั้น: engine ที่รันโค้ด, HTTP server, adapter และ pipeline ของ framework การลดงานที่ Elysia ต้องทำเป็นเพียงส่วนหนึ่งของเส้นทางทั้งหมด

Elysia ยังใช้ความสามารถเฉพาะของ Bun ในเส้นทางที่รองรับ เช่น option `routes` ของ `Bun.serve()` สำหรับ native routing และ `Elysia.file` ที่เลือกใช้ `Bun.file` เมื่อมีให้ใช้งาน ดูรายละเอียดใน[ส่วน Platform Specific Optimization](https://elysiajs.com/internal/jit-compiler#platform-specific-optimization)

ถ้าเทียบ Elysia บน Bun กับ Express บน Node.js ผลที่ได้คือความต่างของทั้ง stack การใช้ runtime เดียวกันช่วยลดตัวแปร แต่ยังต้องดู adapter, HTTP API และ configuration ด้วย จึงจะอธิบายได้ว่ากำลังเปรียบเทียบอะไร

## เทียบกับ Express 5 แบบสั้น ๆ

สำหรับ request `/user?id=42` เราเขียน Express 5 ให้คืนค่า `42` ได้เช่นกัน:

```js
import express from 'express'

const app = express()

app.get('/user', (req, res) => {
  res.send(String(req.query.id))
})
```

Express จัดการ request ผ่าน middleware และ route callbacks ตามลำดับที่ลงทะเบียน โดย middleware อาจจบ response หรือส่งต่อด้วย `next()` เราเลือกได้ว่าจะติดตั้ง parser ให้ทั้งแอปหรือเฉพาะบาง route ตาม [คู่มือ middleware](https://expressjs.com/en/guide/using-middleware/)

ตัวอย่างนี้ไม่ได้ parse JSON body หรือ cookies ให้อัตโนมัติ และ `req.query` ใน Express 5 เป็น getter ที่เรียก query parser ตาม configuration เมื่อเข้าถึงค่า ดู[เอกสารการเปลี่ยนแปลงใน Express 5](https://expressjs.com/en/guide/migrating-5/#req.query) และ[source ของ getter ใน 5.1.0](https://github.com/expressjs/express/blob/v5.1.0/lib/request.js#L208-L218)

ความต่างที่กำลังพิจารณาจึงอยู่ที่วิธีประกอบ pipeline: Elysia ใช้การวิเคราะห์โค้ดร่วมกับข้อมูล route เพื่อสร้างฟังก์ชันเฉพาะ ส่วน Express ให้เราประกอบ middleware และ callbacks ตัวอย่างสั้น ๆ นี้ยังใช้สรุปความเร็วไม่ได้ และยังไม่ได้กำหนดให้ทั้งคู่ตอบเหมือนกันในกรณีไม่มี `id` หรือส่ง query ซ้ำ

## สิ่งที่แลกมากับการสร้าง handler

การประกอบโค้ดมีต้นทุน ถ้า route ใช้เส้นทาง lazy งานนี้จะเพิ่มเข้ามาใน request แรก การเปิด `precompile: true` ย้ายต้นทุนไปช่วงเตรียมแอป จึงควรวัดแยกทั้ง startup time, latency ของการเรียก route ครั้งแรก และผลหลัง warm-up

โค้ดที่สร้างขึ้นต้องอยู่ในหน่วยความจำ ส่วนตัววิเคราะห์และตัวประกอบโค้ดก็เป็นส่วนหนึ่งของ framework ต้นทุนจริงขึ้นอยู่กับจำนวน route, schema และโหมดที่ใช้ ฝั่งผู้ดูแล framework ยังต้อง debug ทั้งตัวสร้างโค้ดและผลลัพธ์ที่มันสร้างด้วย ตาม[หัวข้อ overhead ของ Elysia](https://elysiajs.com/internal/jit-compiler#overhead-of-jit-compiler)

สำหรับ build-time AOT ของ Elysia 2 beta มีข้อแลกเปลี่ยนเพิ่ม: plugin ทำ dry-run แอประหว่าง build จึงต้องจัดการโค้ด initialization ที่เปิด database pool หรือมี side effect และการลงทะเบียน route ต้องสอดคล้องกันระหว่าง build กับ runtime ตาม[ข้อกำหนด Build Time Environment](https://elysiajs.com/blog/elysia-20#build-time-environment)

## แอปจริงจะเร็วขึ้นแค่ไหน?

สำหรับ route ที่ตอบข้อมูลจากหน่วยความจำและมี business logic น้อย framework overhead อาจกินสัดส่วน CPU สูง การลดงานต่อ request จึงมีโอกาสเพิ่ม throughput ได้ชัด

ถ้า latency ส่วนใหญ่เป็นเวลารอฐานข้อมูลหรือ API ภายนอก ผลต่อเวลารวมอาจเล็กกว่า สมมติ request ใช้เวลา 20 ms และมี framework overhead 1 ms ถ้าลดส่วนนี้เหลือ 0.5 ms โดยส่วนอื่นคงเดิม เวลารวมจะเหลือ 19.5 ms หรือลดลง 2.5% ตัวเลขนี้เป็นตัวอย่างคำนวณ ไม่ใช่ผล benchmark ของ Elysia

ภายใต้โหลดสูง ผลอาจต่างออกไป: ถ้า CPU ของแอปเป็นคอขวด การลดงานต่อ request อาจลดเวลารอคิวได้ด้วย จึงควรวัดทั้ง throughput และ latency โดยเฉพาะ p95/p99 ซึ่งบอกเวลาที่ request 95%/99% เสร็จภายใน แทนการดูเฉพาะค่าเฉลี่ย

เวลาประเมิน framework สำหรับ API ของเรา ผมจะเช็กอย่างน้อยสี่เรื่อง:

- **งานที่ทำเท่ากัน:** response, status, headers, validation และ authentication ต้องมีพฤติกรรมตามข้อกำหนดเดียวกัน รวมถึงกรณี input ผิด
- **สภาพแวดล้อมเทียบกันได้:** ระบุ version ของ framework/runtime, adapter, hardware, concurrency และ connection reuse ให้ครบ
- **ช่วงที่วัดชัดเจน:** แยก startup และ request แรกออกจากช่วงหลัง warm-up; operations/second ของการเรียกฟังก์ชันไม่ใช่ requests/second ผ่าน HTTP
- **คอขวดอยู่ตรงไหน:** ดู CPU, memory, error rate และ latency ควบคู่กับฐานข้อมูลและตัวยิงโหลด เพื่อไม่ให้ข้อจำกัดของส่วนอื่นกลบผลของ framework
