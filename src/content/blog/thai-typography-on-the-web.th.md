สวัสดีครับ

บทความเรื่อง typography ภาษาที่ไม่ใช่ละตินบนเว็บ ส่วนใหญ่พูดถึง CJK ส่วนภาษาไทยมักได้พื้นที่แค่บรรทัดเดียวใน font stack แล้วจบ ซึ่งก็คือสิ่งที่ผมทำมาตลอดกับบล็อกนี้เหมือนกัน — ทุกบทความที่นี่มีทั้งอังกฤษและไทย แต่ฝั่งไทยใช้เลย์เอาต์ที่ออกแบบมารอบ serif ภาษาอังกฤษล้วน ๆ

มันก็ดู "โอเคอยู่" ครับ และคำว่า "โอเคอยู่" นี่แหละคือที่ซ่อนของปัญหาแบบนี้ — ตัวหนังสืออ่านออก ไม่มีอะไรทับกันจนสังเกตได้ในแวบเดียว เลยไม่มีใครแจ้งบั๊ก ข้างล่างคือแปดเรื่องที่ผมเจอตอนนั่งดูจริง ๆ เรียงตามความสำคัญคร่าว ๆ — ข้อสุดท้ายเพิ่มเข้ามาหลังโพสต์เผยแพร่ไปแล้ว เพราะการเขียนบทความนี้เองคือสิ่งที่ทำให้เจอมัน

> **แก้สองรอบ วันเดียวกัน** เวอร์ชันแรกเขียนว่าหัวข้อไทยโดน bold *ปลอม* ซึ่งผิด และหัวข้อที่ 1
> ถูกเขียนใหม่ — CSS font matching เลือก face น้ำหนัก 700 ของจริงมาให้ จึงเป็นเรื่องน้ำหนัก
> ไม่ตรงกันระหว่างสองสคริปต์ ไม่ใช่ตัวหนาปลอม พอไปตรวจข้ออ้างนั้นต่อก็เจอเรื่องที่หนักกว่า
> ซึ่งกลายเป็นหัวข้อที่ 8: build ส่งขึ้นไปแต่ subset ละตินของฟอนต์ไทย ตัวอักษรไทยจึงเรนเดอร์
> ด้วยฟอนต์ระบบมาตลอด แก้ทั้งสองอย่างลงรีโปแล้ว ผมเปิดร่องรอยไว้ให้เห็นเพราะข้อผิดอันที่สอง
> สอนอะไรได้มากกว่า

## สรุปก่อน เผื่อยังไม่อยากอ่านยาว

- น้ำหนักหัวข้อค่าเดียว สองภาษาได้ face คนละน้ำหนัก เพราะ CSS font matching ปัดขึ้นไปหาน้ำหนักที่โหลดไว้
- ไทยต้องการ `line-height` มากกว่าละติน ผมใช้ 1.95 เทียบกับ 1.75
- ไทยไม่มี italic — บังคับเมื่อไหร่ได้ตัวเอียงปลอมที่เหมือนตัวอักษรกำลังล้ม
- ย่อหน้าปนไทย-อังกฤษคือกรณีปกติ ไม่ใช่กรณีพิเศษ ลำดับใน font stack จึงสำคัญ
- นับคำด้วยช่องว่างใช้กับไทยไม่ได้ บทความ 6,000 ตัวอักษรจะได้ reading time หนึ่งนาที
- อย่าไปยุ่งกับ `word-break` เบราว์เซอร์ตัดคำไทยเองได้ดีกว่าที่เราไป "ช่วย"
- `toLocaleDateString('th-TH')` ให้ปี **2569** ซึ่งถูกตามราชการ แต่ผิดสำหรับบล็อกเทคโนโลยี

## 1. น้ำหนักเดียว แต่ได้ face คนละตัว

ข้อนี้เปลี่ยนเลย์เอาต์ของผมมากที่สุด

หัวข้อของผมขอ `font-weight: 600` ซึ่งเหมาะกับ serif ภาษาอังกฤษ แต่ละตระกูลเป็น variable font ไฟล์เดียว ที่ถูกประกาศไว้สองน้ำหนักแบบจุด ๆ และนี่คือสิ่งที่ build พ่นออกมาจริง ๆ:

```
Source Serif 4    font-weight: 400, 600
Noto Serif Thai   font-weight: 400, 700
```

ละตินมี 600 ส่วนไทยไม่มี — ไม่ใช่เพราะตระกูลฟอนต์ไม่มีนะครับ (Noto Serif Thai มีตั้งแต่ 100 ถึง 900) แต่เพราะผมประกาศไว้แค่สองน้ำหนัก

มีเรื่องที่ทำให้ผมแปลกใจตอนตรวจ: ทุกน้ำหนักที่ประกาศไว้ชี้ไปที่ **ไฟล์ woff2 ไฟล์เดียวกัน** การเพิ่ม 600 เข้าไปในรายการจึงได้ `@font-face` เพิ่มอีกก้อนที่ชี้ URL เดิม และ **ไม่ได้ดาวน์โหลดอะไรเพิ่มเลย** คำแนะนำว่า "โหลดน้ำหนักให้น้อยเข้าไว้" ใช้ได้ดีกับฟอนต์ static แต่แทบไม่มีความหมายกับ variable font — สิ่งที่เรากำลังเลือกคือจำนวนจุดบนแกนที่เบราว์เซอร์จับคู่ได้ ไม่ใช่จำนวนไบต์ที่ส่งไป

แล้วเบราว์เซอร์ทำยังไงกับ 600 ที่มันหาไม่เจอ? ไม่ใช่อย่างที่ผมเดาไว้ครับ กฎ font matching ของ CSS บอกว่าเมื่อน้ำหนักที่ขอ **มากกว่า 500** เบราว์เซอร์จะมองหาน้ำหนักที่ *เท่ากับหรือมากกว่า* ค่าที่ขอก่อน โดยไล่จากน้อยไปมาก — 600 มากกว่า 500 และมี 700 อยู่ ตัวไทยจึงเรนเดอร์ด้วย face **น้ำหนัก 700 ของจริง**

แปลว่าหัวข้อบรรทัดเดียวกำลังตั้งละตินไว้ที่ 600 และตั้งไทยไว้ที่ 700 — เป็นเรื่องน้ำหนักไม่ตรงกันระหว่างสองสคริปต์ ไม่ใช่สิ่งแปลกปลอมจากการเรนเดอร์ (พร้อมข้อแม้จากหัวข้อที่ 8: ก่อนที่ผมจะแก้เรื่อง subset น้ำหนัก 700 ของไทยนั้นมาจากฟอนต์ระบบ ไม่ได้มาจากตระกูลที่ผมคิดว่าโหลดไว้) และมันทบกันด้วย เพราะตัวอักษรไทยมีน้ำหนักสายตาต่อตัวมากกว่า serif ละตินที่น้ำหนักตัวเลขเท่ากันอยู่แล้ว ที่ขนาด 3rem หัวข้อไทยจึงไม่ได้แค่ดูหนากว่านิดหน่อย แต่ดูเหมือนกำลังตะโกน

วิธีแก้คือเลิกปล่อยให้ fallback ตัดสินใจ แล้ว map ภาษาไทยไปยังน้ำหนักที่โหลดมาจริง:

```css
:lang(th) h2,
:lang(th) h3 {
	font-weight: 700;
}

:lang(th) h1 {
	font-weight: 400;
}
```

ขอพูดให้ชัดว่ากฎแต่ละข้อทำอะไร กฎ `h1` คือตัวที่เปลี่ยนการเรนเดอร์จริง — หัวข้อขนาดใหญ่ลดจาก 700 มาที่ **400** ซึ่งเป็นส่วนที่ผมไม่ได้คาดไว้จนกระทั่งเอาสองภาษามาวางข้างกันที่ขนาดเต็ม ส่วนกฎ `h2`/`h3` วันนี้ไม่ได้เปลี่ยนอะไรเลย เพราะ 600 มันปัดไปเป็น 700 อยู่แล้ว — มันทำหน้าที่ตรึงเจตนาไว้ เผื่อวันหลังโหลดน้ำหนัก 600 ของไทยเข้ามาแล้วหัวข้อย่อยทั้งเว็บจะได้ไม่เปลี่ยนหน้าตาเงียบ ๆ

### แล้ว bold ปลอมอยู่ตรงไหน

ตัวหนาสังเคราะห์เป็นอันตรายจริงสำหรับภาษาไทย และมันทำให้วรรณยุกต์กับสระบนเละอย่างที่กลัวกันจริง ๆ เพียงแต่มันไม่ใช่บั๊กของผม เบราว์เซอร์จะสังเคราะห์ให้ก็ต่อเมื่อ face ที่มันเลือกได้ **เบากว่า** ที่เราขอ — ซึ่งเกิดเมื่อโหลดมาแค่ 400 แล้วไปขอ 700 อันเป็นสถานการณ์ปกติของการเอาฟอนต์ไทยไปแปะใส่ดีไซน์ที่มีอยู่แล้วโดยไม่กลับไปดูเรื่องน้ำหนักอีกเลย

เวอร์ชันทั่วไปของกับดักนี้อยู่เหนือทั้งสองกลไก: **ทุกน้ำหนักใน type scale ของคุณถูก resolve แยกกันในแต่ละตระกูลฟอนต์ และไม่มีอะไรบอกคุณว่ามันไป resolve เป็นอะไร** ไม่มี warning ใน console ว่า "ตรงนี้ไทยได้น้ำหนักไม่เท่าละติน" ให้ไล่เทียบ scale กับกฎ `@font-face` ที่ build พ่นออกมาจริง ไม่ใช่กับที่หน้าเว็บผู้ให้บริการฟอนต์บอกว่ามี

## 2. ไทยต้องการระยะบรรทัดมากกว่าละติน

เพราะการซ้อนในแนวตั้งนั่นแหละ `line-height` ที่สบายตาสำหรับอังกฤษจะแน่นเกินไปสำหรับไทย หางตัวอักษรกับสระบนของบรรทัดข้างเคียงเริ่มเบียดกัน

```css
body {
	line-height: 1.75;
}

:lang(th) p,
:lang(th) li {
	line-height: 1.95;
}
```

1.75 เป็น 1.95 ฟังดูเหมือนเศษทศนิยม แต่ไม่ใช่ครับ ลองวางย่อหน้าสองภาษาที่ค่าเท่ากันดู ย่อหน้าไทยจะอ่านออกมาเป็นก้อนที่ทึบกว่า ซึ่งเป็นสิ่งที่เราไม่ต้องการเลยในบทความที่คนต้องอ่านยี่สิบนาที

หัวข้อก็ต้องจัดการแบบเดียวกันแต่กลับทิศ — ระยะบรรทัดแน่น ๆ ที่ทำให้หัวข้ออังกฤษดูดี จะทำให้สระกับวรรณยุกต์ไทยชนกัน หัวข้อไทยจึงดันกลับขึ้นไปที่ 1.45 ขณะที่ฝั่งอังกฤษอยู่ที่ 1.15 สำหรับ `h1` และ 1.22 สำหรับระดับรองลงมา

## 3. ไทยไม่มีตัวเอียง

อักษรไทยไม่มีธรรมเนียม italic พอสั่งไป เบราว์เซอร์จะเอียงตัวอักษรให้แบบกลไก ผลที่ได้เหมือนตัวหนังสือกำลังล้มมากกว่ากำลังถูกเน้น

blockquote ของผมเป็นตัวเอียง จึงต้อง:

```css
:lang(th) blockquote {
	font-style: normal;
}
```

ภาษาไทยเน้นข้อความด้วยน้ำหนัก ระยะห่าง หรือด้วยโครงสร้างประโยคไปเลย ถ้าดีไซน์ของคุณพึ่ง italic กับอะไรที่สำคัญ — caption, คำพูดอ้างอิง, ป้ายกำกับรูป — มันต้องมีแผนสองสำหรับภาษาไทย

## 4. ย่อหน้าปนสองภาษาคือกรณีปกติ

งานเขียนสายเทคภาษาไทยไม่ได้มีภาษาเดียว ประโยคจริงหน้าตาแบบนี้:

> Concurrency 10 ขึ้นไป CPU ของ API ตันอยู่ราว 113% ขณะที่ PostgreSQL ใช้ 180–430%

คำละติน ไวยากรณ์ไทย และตัวเลข อยู่ในบรรทัดเดียวกัน แปลว่า font stack ไม่ใช่เรื่อง "เลือกฟอนต์ไทยให้หน้าภาษาไทย" — ฟอนต์สองตัวเรนเดอร์อยู่ในย่อหน้าเดียวกันตลอดเวลา ลำดับจึงสำคัญ:

```css
--stack-body: var(--font-serif), var(--font-thai), Georgia, serif;
```

serif ละตินมาก่อนและรับงานภาษาละติน มันไม่มี glyph ไทย ตัวไทยจึงตกไปที่ Noto Serif Thai ถ้าสลับลำดับ glyph ละตินของฟอนต์ไทยจะเข้ามายึดข้อความภาษาอังกฤษของคุณแทน ซึ่งเป็นปัญหาคนละแบบและแย่กว่า

สิ่งที่ต้องตรวจหลังตั้งค่าเสร็จ ไม่ใช่ "ตัวไทยขึ้นไหม" (ขึ้นอยู่แล้ว) แต่คือสองฟอนต์นั้นดูเป็นย่อหน้าเดียวกันหรือเปล่า ถ้าความสูง x-height หรือน้ำหนักไม่ตรงกัน ทุกคำภาษาอังกฤษในประโยคไทยจะเด้งออกมาเหมือนถูกไฮไลต์

## 5. การนับคำใช้ไม่ได้

ผมอยากได้ reading time วิธีมาตรฐานคือ split ด้วยช่องว่างแล้วหารด้วย 200 กว่า ๆ คำต่อนาที แต่ภาษาไทยไม่เว้นวรรคระหว่างคำ บทความไทย 6,000 ตัวอักษรจึง split ได้ "คำ" ไม่กี่สิบ แล้วรายงานว่าอ่านหนึ่งนาที

แยกนับสองสคริปต์แล้วจบ:

```ts
const thaiChars = (prose.match(/[฀-๿]/g) ?? []).length;
const latinWords = prose
	.replace(/[฀-๿]+/g, ' ')
	.split(/\s+/)
	.filter(Boolean).length;

const minutes = latinWords / WORDS_PER_MINUTE + thaiChars / THAI_CHARS_PER_MINUTE;
```

ผมใช้ 220 คำต่อนาที และ 700 อักขระไทยต่อนาที ตัวเลขฝั่งไทยเป็นค่าประมาณที่ใช้งานได้ ไม่ใช่ค่าที่ผมวัดมา ให้ถือเป็นลูกบิดที่ปรับได้ ไม่ใช่ค่าคงที่

## 6. อย่าไปยุ่งกับ `word-break`

เพราะไทยไม่มีช่องว่างระหว่างคำ เบราว์เซอร์จึงตัดบรรทัดด้วยการแบ่งคำจากพจนานุกรมของตัวเอง ซึ่งทำได้ดีพอสมควร อะไรก็ตามที่เราไป "ช่วย" — `word-break: break-all` หรือ `overflow-wrap: anywhere` แบบ global — จะไปทับกลไกนั้นแล้วได้การตัดกลางคำ

ผมเก็บ `overflow-wrap: break-word` ไว้ที่ `body` เพื่อ URL ยาว ๆ นอกนั้นปล่อยเรื่องการตัดบรรทัดไว้เฉย ๆ

## 7. ปีนี้ไม่ใช่ 2569

`toLocaleDateString('th-TH')` ให้ปีพุทธศักราชเป็นค่าเริ่มต้น โพสต์ปี 2026 จึงลงวันที่เป็น **2569** ซึ่งถูกต้องตามการใช้งานทั่วไปในไทย แต่ผิดสำหรับบล็อกเทคโนโลยี ที่คนอ่านกำลังเทียบผล benchmark กับเวอร์ชันซอฟต์แวร์และวันปล่อยของที่เป็นคริสต์ศักราช

```ts
dateLocale: 'th-TH-u-ca-gregory', // Gregorian, not Buddhist era — a 2569 would confuse a tech post
```

ส่วนขยาย `-u-ca-gregory` ยังคงชื่อเดือนภาษาไทยไว้ — `ก.ย.` — และเปลี่ยนแค่ปฏิทิน แต่มัน**ไม่ได้**เปลี่ยนตัวเลข เพราะ `th-TH` resolve ระบบตัวเลขเป็น `latn` อยู่แล้ว วันที่กับปีจึงเป็นเลขอารบิกมาตั้งแต่ต้น ถ้าอยากได้เลขไทยต้องขอแยกด้วย `-u-nu-thai` ซึ่งจะได้ `๑๓ ก.ย. ๒๐๒๖`

อีกเรื่องที่เจอในรอบเดียวกันแต่อยู่ฝั่งอังกฤษ และแปลกกว่าที่เห็นตอนแรก: ผมจัดรูปแบบวันที่ด้วย `toLocaleDateString('en-GB', { month: 'short' })` บนเครื่องผมมันให้ `SEP` แต่บนเว็บที่ deploy แล้วมันให้ **SEPT** — สี่ตัวอักษร ขณะที่เดือนอื่นได้สามตัว

โค้ดเดียวกัน input เดียวกัน ได้คำตอบสองแบบ เพราะตัวย่อมาจากข้อมูล CLDR ที่มากับ ICU ของ runtime นั้น ๆ และข้อมูลรุ่นใหม่สะกด `en-GB` ว่า `Sept` — เครื่องผมกับ container ที่ build อยู่คนละเวอร์ชันกัน คอลัมน์วันที่จึงกว้างกว่าเพื่อนหนึ่งตัวอักษร ปีละหนึ่งเดือน แต่เกิดเฉพาะบน production

แถมเว็บยังขัดแย้งกันเองด้วย: หัวบทความวิ่งผ่าน `toLocaleDateString` ส่วนหน้า listing ใช้ array ชื่อเดือนที่ hardcode ไว้ โพสต์เดียวกันจึงเป็น `SEPT` ที่หัวบทความ แต่เป็น `SEP` ในหน้ารวม ตอนนี้ทั้งสองที่ดึงจากตารางตัวย่อสามตัวอักษรชุดเดียวกัน ซึ่งให้ผลเหมือนกันทุก runtime — สำหรับรายการสิบสองช่องที่ไม่มีวันเปลี่ยน กลไก locale ไม่ได้ให้อะไรผมเลย แถมคิดค่าเป็นความต่างที่ผมมองไม่เห็นบนเครื่องตัวเอง

## 8. ฟอนต์ไม่เคยถูกโหลดมาสำหรับภาษาไทยเลย

ข้อนี้ผมเจอเพราะไปตรวจหัวข้อข้างบน การวิเคราะห์เรื่องน้ำหนักจะมีความหมายก็ต่อเมื่อ Noto Serif Thai เป็นฟอนต์ที่วาดตัวอักษรไทยจริง ผมจึงไปเปิดดูกฎ `@font-face` ที่ build พ่นออกมา แล้วพบว่าทุกก้อนหน้าตาแบบนี้:

```
unicode-range: U+0000-00FF, U+0131, U+0152-0153, U+02BB-02BC, ...
```

นั่นคือละตินครับ **ไม่มี face ไหนเลยในเว็บที่ build ออกมา ที่ครอบช่วง U+0E01–U+0E5B** ซึ่งเป็นบล็อกอักษรไทย ผมตั้งค่าฟอนต์ไทยไว้ อ้างถึงมันในทุก stack เขียนกฎเจาะจง `:lang(th)` — แล้ว deploy build ที่เรนเดอร์ตัวอักษรไทยจากฟอนต์นั้นไม่ได้แม้แต่ตัวเดียว ตัวอักษรไทยทั้งเว็บมาจากฟอนต์ที่ระบบปฏิบัติการเลือกให้หลังจากไล่ stack จนหมด

ต้นเหตุคือค่า default ครับ ผมไม่เคยระบุ subset ไว้ในคอนฟิกของ font provider และรายการ default เอนไปทางละติน ตระกูลฟอนต์ไทยจึงถูกดึงมาโดยที่ glyph ไทยถูกตัดทิ้ง:

```js
{
	name: 'Noto Serif Thai',
	cssVariable: '--font-thai',
	weights: [400, 700],
	styles: ['normal'],
	subsets: ['thai', 'latin'],
}
```

พอเพิ่มบรรทัดนั้น build ก็พ่นไฟล์ที่สองออกมา โดยมีช่วงเป็น `U+02D7, U+0303, U+0331, U+0E01-0E5B, U+200C-200D, U+25CC` — บล็อกอักษรไทย บวกเครื่องหมายประกอบ และวงกลมประจุดที่ใช้แสดงสระหรือวรรณยุกต์ที่ลอยเดี่ยว ไฟล์นี้คือสิ่งที่ควรอยู่ตรงนั้นตั้งแต่แรก

มีสองเรื่องที่ทำให้ข้อนี้มีค่ามากกว่าการเป็นเชิงอรรถน่าอาย

เรื่องแรกคือ **มันดูดีอยู่** macOS เลือกฟอนต์ไทยของระบบที่ใช้งานได้ดีมาให้ หน้าเว็บจึงแสดงภาษาไทยที่อ่านออก และผมก็นั่งปรับระยะบรรทัดกับน้ำหนักทั้งคืนให้กับฟอนต์ที่ไม่เคยถูกใช้เลย ทุกการตัดสินใจด้วยสายตาในหัวข้อข้างบนถูกตัดสินบน fallback

เรื่องที่สองคือรูปแบบทั่วไปของมัน: **font stack ที่เราเขียน ไม่ใช่ font stack ที่ถูกส่งขึ้นไป** วิธีตรวจใช้เวลาสิบวินาที — ค้นใน output ที่ build แล้ว ว่ามีอะไรครอบช่วงยูนิโค้ดของสคริปต์ที่เราใช้หรือเปล่า:

```sh
grep -o "unicode-range:[^;]*" dist/**/*.html | grep "U+0E"
```

ถ้าผลออกมาว่างเปล่าทั้งที่เว็บมีข้อความไทยอยู่ ฟอนต์ใน CSS ของคุณเป็นแค่ของประดับครับ

## ถ้าย้อนกลับไปได้จะทำอะไรต่างออกไป

จัดหน้าภาษาไทยก่อน หรืออย่างน้อยก็จัดพร้อมกันทั้งสองภาษา ทุกข้อข้างบนคือกรณีที่การตัดสินใจซึ่งถูกต้องสำหรับภาษาอังกฤษ ไหลเข้าไปในสคริปต์ที่ไม่เคยถูกตรวจสอบเงียบ ๆ ไม่มีข้อไหนสร้าง error, warning หรือทำให้ build พัง เลย์เอาต์แค่ค่อย ๆ แย่ลงในภาษาที่ผมไม่ได้มอง

วิธีตรวจที่ถูกที่สุดเท่าที่ผมรู้: เอาบทความเดียวกันสองภาษามาวางข้างกันที่ความกว้างเดสก์ท็อปเต็ม แล้วมองมันเป็น**ภาพ** ไม่ใช่เป็นตัวหนังสือ น้ำหนักที่ไม่เข้ากัน ระยะบรรทัดที่แน่นเกิน และ bold ปลอม จะโผล่ให้เห็นทันที และไม่มีอันไหนโผล่เลยตอนที่เราอ่านทีละภาษา
