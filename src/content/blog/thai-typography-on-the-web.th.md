สวัสดีครับ

บทความเรื่อง typography ภาษาที่ไม่ใช่ละตินบนเว็บ ส่วนใหญ่พูดถึง CJK ส่วนภาษาไทยมักได้พื้นที่แค่บรรทัดเดียวใน font stack แล้วจบ ซึ่งก็คือสิ่งที่ผมทำมาตลอดกับบล็อกนี้เหมือนกัน — ทุกบทความที่นี่มีทั้งอังกฤษและไทย แต่ฝั่งไทยใช้เลย์เอาต์ที่ออกแบบมารอบ serif ภาษาอังกฤษล้วน ๆ

มันก็ดู "โอเคอยู่" ครับ และคำว่า "โอเคอยู่" นี่แหละคือที่ซ่อนของปัญหาแบบนี้ — ตัวหนังสืออ่านออก ไม่มีอะไรทับกันจนสังเกตได้ในแวบเดียว เลยไม่มีใครแจ้งบั๊ก ข้างล่างคือเจ็ดเรื่องที่ผมเจอตอนนั่งดูจริง ๆ เรียงตามความสำคัญคร่าว ๆ

## สรุปก่อน เผื่อยังไม่อยากอ่านยาว

- ถ้าน้ำหนักที่ theme ขอ ไม่ได้ถูก **โหลด** มา เบราว์เซอร์จะสังเคราะห์ bold ให้ และกับไทยมันทำให้วรรณยุกต์กับสระบนเละ
- ไทยต้องการ `line-height` มากกว่าละติน ผมใช้ 1.95 เทียบกับ 1.75
- ไทยไม่มี italic — บังคับเมื่อไหร่ได้ตัวเอียงปลอมที่เหมือนตัวอักษรกำลังล้ม
- ย่อหน้าปนไทย-อังกฤษคือกรณีปกติ ไม่ใช่กรณีพิเศษ ลำดับใน font stack จึงสำคัญ
- นับคำด้วยช่องว่างใช้กับไทยไม่ได้ บทความ 6,000 ตัวอักษรจะได้ reading time หนึ่งนาที
- อย่าไปยุ่งกับ `word-break` เบราว์เซอร์ตัดคำไทยเองได้ดีกว่าที่เราไป "ช่วย"
- `toLocaleDateString('th-TH')` ให้ปี **2569** ซึ่งถูกตามราชการ แต่ผิดสำหรับบล็อกเทคโนโลยี

## 1. bold ปลอมทำให้วรรณยุกต์เละ

ข้อนี้เปลี่ยนเลย์เอาต์ของผมมากที่สุด

อักษรไทยซ้อนในแนวตั้ง หนึ่งพยางค์อาจมีสระบน มีวรรณยุกต์อยู่เหนือขึ้นไปอีก และมีสระล่างใต้พยัญชนะ — สี่ชั้นในกล่องบรรทัดเดียว พอเบราว์เซอร์หาน้ำหนักที่เราขอไม่เจอ มันไม่ยอมแพ้ครับ มันปลอมให้ โดยการถ่างตัวอักษรออก บนภาษาละตินผลคือ bold ที่ดูเละนิดหน่อย แต่บนภาษาไทยมันไปทำให้วรรณยุกต์หนาขึ้นและช่องว่างระหว่างชั้นที่ซ้อนกันปิดเข้าหากัน

หัวข้อของผมขอ `font-weight: 600` ซึ่งเหมาะกับ serif ภาษาอังกฤษ ส่วน Noto Serif Thai เองก็**มี** 600 นะครับ (ตระกูลนี้มีตั้งแต่ 100 ถึง 900) แต่ผมโหลดมาแค่ 400 กับ 700:

```js
{
	provider: fontProviders.google(),
	name: 'Noto Serif Thai',
	cssVariable: '--font-thai',
	weights: [400, 700],
	styles: ['normal'],
}
```

หัวข้อภาษาไทยจึงไปขอน้ำหนักที่เบราว์เซอร์ไม่มีอยู่ในมือ แล้วได้ของปลอมกลับมา วิธีแก้คือ map ภาษาไทยไปยังน้ำหนักที่โหลดมาจริง:

```css
:lang(th) h2,
:lang(th) h3 {
	font-weight: 700;
}

:lang(th) h1 {
	font-weight: 400;
}
```

หัวข้อย่อยใช้ 700 ของจริง ส่วนหัวข้อขนาดใหญ่ถอยลงมาที่ **400** ซึ่งเป็นส่วนที่ผมไม่ได้คาดไว้ล่วงหน้า: ที่ขนาด 3rem หัวข้อไทยน้ำหนัก 700 ตะโกนใส่หัวข้ออังกฤษน้ำหนัก 600 เพราะตัวอักษรไทยมีน้ำหนักสายตาต่อตัวมากกว่าอยู่แล้ว ผมรู้เรื่องนี้ได้ก็ต่อเมื่อเอาสองภาษามาวางข้างกันที่ขนาดเต็ม

เวอร์ชันทั่วไปของหลุมนี้คือ: **น้ำหนักไหนใน type scale ที่ฟอนต์ non-Latin ของคุณไม่ได้โหลดไว้ จะถูกสังเคราะห์ขึ้นเงียบ ๆ** ไม่มี warning ใน console ให้ไล่เทียบ scale กับรายการ `@font-face` ที่โหลดจริง ไม่ใช่กับสิ่งที่ตระกูลฟอนต์รองรับในทางทฤษฎี

## 2. ไทยต้องการระยะบรรทัดมากกว่าละติน

เพราะการซ้อนในแนวตั้งนั่นแหละ `line-height` ที่สบายตาสำหรับอังกฤษจะแน่นเกินไปสำหรับไทย หางตัวอักษรกับสระบนของบรรทัดข้างเคียงเริ่มเบียดกัน

```css
body {
	line-height: 1.75;
}

:lang(th) p,
:lang(th) li {
	line-height: 1.95;
}
```

1.75 เป็น 1.95 ฟังดูเหมือนเศษทศนิยม แต่ไม่ใช่ครับ ลองวางย่อหน้าสองภาษาที่ค่าเท่ากันดู ย่อหน้าไทยจะอ่านออกมาเป็นก้อนที่ทึบกว่า ซึ่งเป็นสิ่งที่เราไม่ต้องการเลยในบทความที่คนต้องอ่านยี่สิบนาที

หัวข้อก็ต้องจัดการแบบเดียวกันแต่กลับทิศ — ระยะบรรทัดแน่น ๆ ที่ทำให้หัวข้ออังกฤษดูดี จะทำให้สระกับวรรณยุกต์ไทยชนกัน ของผมจึงดันกลับขึ้นไปที่ 1.45 ขณะที่อังกฤษอยู่ที่ 1.15

## 3. ไทยไม่มีตัวเอียง

อักษรไทยไม่มีธรรมเนียม italic พอสั่งไป เบราว์เซอร์จะเอียงตัวอักษรให้แบบกลไก ผลที่ได้เหมือนตัวหนังสือกำลังล้มมากกว่ากำลังถูกเน้น

blockquote ของผมเป็นตัวเอียง จึงต้อง:

```css
:lang(th) blockquote {
	font-style: normal;
}
```

ภาษาไทยเน้นข้อความด้วยน้ำหนัก ระยะห่าง หรือด้วยโครงสร้างประโยคไปเลย ถ้าดีไซน์ของคุณพึ่ง italic กับอะไรที่สำคัญ — caption, คำพูดอ้างอิง, ป้ายกำกับรูป — มันต้องมีแผนสองสำหรับภาษาไทย

## 4. ย่อหน้าปนสองภาษาคือกรณีปกติ

งานเขียนสายเทคภาษาไทยไม่ได้มีภาษาเดียว ประโยคจริงหน้าตาแบบนี้:

> Concurrency 10 ขึ้นไป CPU ของ API ตันอยู่ราว 113% ขณะที่ PostgreSQL ใช้ 180–430%

คำละติน ไวยากรณ์ไทย และตัวเลข อยู่ในบรรทัดเดียวกัน แปลว่า font stack ไม่ใช่เรื่อง "เลือกฟอนต์ไทยให้หน้าภาษาไทย" — ฟอนต์สองตัวเรนเดอร์อยู่ในย่อหน้าเดียวกันตลอดเวลา ลำดับจึงสำคัญ:

```css
--stack-body: var(--font-serif), var(--font-thai), Georgia, serif;
```

serif ละตินมาก่อนและรับงานภาษาละติน มันไม่มี glyph ไทย ตัวไทยจึงตกไปที่ Noto Serif Thai ถ้าสลับลำดับ glyph ละตินของฟอนต์ไทยจะเข้ามายึดข้อความภาษาอังกฤษของคุณแทน ซึ่งเป็นปัญหาคนละแบบและแย่กว่า

สิ่งที่ต้องตรวจหลังตั้งค่าเสร็จ ไม่ใช่ "ตัวไทยขึ้นไหม" (ขึ้นอยู่แล้ว) แต่คือสองฟอนต์นั้นดูเป็นย่อหน้าเดียวกันหรือเปล่า ถ้าความสูง x-height หรือน้ำหนักไม่ตรงกัน ทุกคำภาษาอังกฤษในประโยคไทยจะเด้งออกมาเหมือนถูกไฮไลต์

## 5. การนับคำใช้ไม่ได้

ผมอยากได้ reading time วิธีมาตรฐานคือ split ด้วยช่องว่างแล้วหารด้วย 200 กว่า ๆ คำต่อนาที แต่ภาษาไทยไม่เว้นวรรคระหว่างคำ บทความไทย 6,000 ตัวอักษรจึง split ได้ "คำ" ไม่กี่สิบ แล้วรายงานว่าอ่านหนึ่งนาที

แยกนับสองสคริปต์แล้วจบ:

```ts
const thaiChars = (prose.match(/[฀-๿]/g) ?? []).length;
const latinWords = prose
	.replace(/[฀-๿]+/g, ' ')
	.split(/\s+/)
	.filter(Boolean).length;

const minutes = latinWords / WORDS_PER_MINUTE + thaiChars / THAI_CHARS_PER_MINUTE;
```

ผมใช้ 220 คำต่อนาที และ 700 อักขระไทยต่อนาที ตัวเลขฝั่งไทยเป็นค่าประมาณที่ใช้งานได้ ไม่ใช่ค่าที่ผมวัดมา ให้ถือเป็นลูกบิดที่ปรับได้ ไม่ใช่ค่าคงที่

## 6. อย่าไปยุ่งกับ `word-break`

เพราะไทยไม่มีช่องว่างระหว่างคำ เบราว์เซอร์จึงตัดบรรทัดด้วยการแบ่งคำจากพจนานุกรมของตัวเอง ซึ่งทำได้ดีพอสมควร อะไรก็ตามที่เราไป "ช่วย" — `word-break: break-all` หรือ `overflow-wrap: anywhere` แบบ global — จะไปทับกลไกนั้นแล้วได้การตัดกลางคำ

ผมเก็บ `overflow-wrap: break-word` ไว้ที่ `body` เพื่อ URL ยาว ๆ นอกนั้นปล่อยเรื่องการตัดบรรทัดไว้เฉย ๆ

## 7. ปีนี้ไม่ใช่ 2569

`toLocaleDateString('th-TH')` ให้ปีพุทธศักราชเป็นค่าเริ่มต้น โพสต์ปี 2026 จึงลงวันที่เป็น **2569** ซึ่งถูกต้องตามการใช้งานทั่วไปในไทย แต่ผิดสำหรับบล็อกเทคโนโลยี ที่คนอ่านกำลังเทียบผล benchmark กับเวอร์ชันซอฟต์แวร์และวันปล่อยของที่เป็นคริสต์ศักราช

```ts
dateLocale: 'th-TH-u-ca-gregory', // Gregorian, not Buddhist era — a 2569 would confuse a tech post
```

ส่วนขยาย `-u-ca-gregory` ยังคงชื่อเดือนภาษาไทยและรูปแบบตัวเลขแบบไทยไว้ เปลี่ยนแค่ปฏิทิน

อีกเรื่องที่เจอในรอบเดียวกันแต่อยู่ฝั่งอังกฤษ: ผมจัดรูปแบบวันที่ด้วย `en-GB` ซึ่งย่อ September เป็น **SEPT** — สี่ตัวอักษร ขณะที่เดือนอื่นได้สามตัว ในคอลัมน์วันที่ที่ความกว้างคงที่ จะมีอยู่แถวหนึ่งกว้างกว่าเพื่อน ปีละหนึ่งเดือน

## ถ้าย้อนกลับไปได้จะทำอะไรต่างออกไป

จัดหน้าภาษาไทยก่อน หรืออย่างน้อยก็จัดพร้อมกันทั้งสองภาษา ทุกข้อข้างบนคือกรณีที่การตัดสินใจซึ่งถูกต้องสำหรับภาษาอังกฤษ ไหลเข้าไปในสคริปต์ที่ไม่เคยถูกตรวจสอบเงียบ ๆ ไม่มีข้อไหนสร้าง error, warning หรือทำให้ build พัง เลย์เอาต์แค่ค่อย ๆ แย่ลงในภาษาที่ผมไม่ได้มอง

วิธีตรวจที่ถูกที่สุดเท่าที่ผมรู้: เอาบทความเดียวกันสองภาษามาวางข้างกันที่ความกว้างเดสก์ท็อปเต็ม แล้วมองมันเป็น**ภาพ** ไม่ใช่เป็นตัวหนังสือ น้ำหนักที่ไม่เข้ากัน ระยะบรรทัดที่แน่นเกิน และ bold ปลอม จะโผล่ให้เห็นทันที และไม่มีอันไหนโผล่เลยตอนที่เราอ่านทีละภาษา
