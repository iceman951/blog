[คราวที่แล้ว](/blog/bun-http-framework-benchmark-on-m5-air/) ผมวัดว่า Bun HTTP Framework แปดตัวเร็วแค่ไหนบนเครื่องนี้

และสิ่งที่น่าสนใจที่สุดกลับไม่ใช่ว่า Framework ตัวไหนเร็วที่สุด แต่เป็นความผิดพลาดที่ผมเกือบ Publish ไปแล้ว คือการรันติดกันทำให้ Benchmark วัดความร้อนของเครื่อง แทนที่จะวัด Framework

รอบนี้ผมอยากรู้อีกเรื่อง

Express ช้ากว่า Elysia 2.3 เท่า แล้วมันกินพลังงานต่อ Request มากกว่า 2.3 เท่าไหม?

ไม่มีใครตีพิมพ์ค่าจูลต่อ Request ของ JavaScript Framework และบนโน้ตบุ๊กที่ไม่มีพัดลม ทุกวัตต์จะกลายเป็นความร้อนที่ไม่มีที่ไป ผมเลยคิดว่ามันน่ารู้

คำตอบสั้น ๆ คือ **1.8 เท่า** ไม่ใช่ 2.3 เท่า

เหตุผลคือ Express ดึงไฟได้ไม่มากเท่า Elysia

ส่วนคำตอบยาว ๆ คือพลังงานส่วนใหญ่ที่ผมวัดได้ ไม่ได้เป็นของ Framework เลย

| แรม | 24 GB unified |
| ระบบปฏิบัติการ | macOS 26.6.2 (25G83) |
| Bun | 1.4.0 |

macOS 26 เรียกคอร์ประสิทธิภาพสูงว่า "Super" ไม่ใช่ "Performance" ซึ่งมีผลจริงในภายหลัง — เป็นเหตุผลที่ความพยายามอ่านความถี่ต่อ cluster ครั้งแรกของผมได้ค่าว่างเปล่า

โพสต์ก่อนรันที่ 25 °C โพสต์นี้ที่ 22 °C **ตัวเลข throughput ในนี้จึงเทียบกับโพสต์นั้นไม่ได้** บนเครื่องระบายความร้อนแบบ passive อุณหภูมิห้องคือพารามิเตอร์ ไม่ใช่เรื่องปลีกย่อย

## powermetrics วัดอะไร และไม่วัดอะไร

ทุกอย่างข้างล่างมาจาก `powermetrics` ที่ sample 2 ครั้งต่อวินาที บน Apple Silicon มันให้ตัวสะสมพลังงานต่อ sample เป็นมิลลิจูล:

```
cpu_energy + gpu_energy + ane_energy
```

ตัวเลขนั้นคือ **พลังงานประมวลผลของ SoC เท่านั้น** มันไม่รวม:

- **DRAM** บนสถาปัตยกรรม unified memory ส่วนนี้มีจริง ผันตามโหลด และเป็นส่วนที่ framework ซึ่ง allocate หนักกว่าจะเผามากกว่าพอดี นี่คือสิ่งที่หายไปแล้วกระทบคำถามของผมมากที่สุด จึงต้องพูดก่อน ไม่ใช่ซ่อนไว้เชิงอรรถ
- SoC fabric, interconnect และ memory controller
- จอและ backlight — บ่อยครั้งเป็นตัวกินไฟมากที่สุดตัวเดียวบนโน้ตบุ๊ก
- SSD, Wi-Fi, Bluetooth, Secure Enclave และโดเมน always-on
- การสูญเสียจากการแปลงไฟที่ PMU/VRM และที่ตัว adapter เอง

ทุกตัวเลขในโพสต์นี้จึงเป็น **มิลลิจูลของพลังงานประมวลผล SoC ต่อ request** ไม่ใช่มิลลิจูลที่ปลั๊กไฟ พลังงานที่ปลั๊กสูงกว่านี้อย่างมีนัยสำคัญ powermetrics เองก็บอกไว้ และคำเตือนของมันน่าอ้างอิง เพราะมันอนุญาตการใช้งานแบบนี้พอดี และห้ามการตีความเกินเลยพอดี:

> Average power values reported by powermetrics are estimated and may be inaccurate - hence they should not be used for any comparison between devices, but can be used to help optimize apps for energy efficiency.

เทียบ framework บนเครื่องเดียวกัน: ได้ เทียบเครื่องนี้กับเครื่องคุณ: ไม่ได้

## วิธีการ

Framework ที่นำมาทดสอบมีห้าตัวบน Bun คือ `elysia`, `hono`, `bun` (`Bun.serve` ดิบ ไม่มี Framework), `effect` และ `express` ครอบคลุมช่วงผลลัพธ์ทั้งหมดของโพสต์ก่อน

ห้า Round รอบละหนึ่งครั้ง รวม **25 Measurements** สี่ Route ต่อการวัด Route ละ 10 วินาทีที่ 500 Concurrent Connections ส่วน Video ใช้ 10

### ปัญหาเรื่องลำดับ อีกครั้ง

โพสต์ก่อนพิสูจน์แล้วว่าบนเครื่องนี้การรันไล่กันทำให้ throughput ลดลงราว 15% จากช่องแรกถึงช่องสุดท้าย คราวนั้นแก้ด้วยการสุ่มลำดับ คราวนี้ผมใช้ **cyclic Latin square ขนาด 5×5** แทน:

```
      slot1   slot2   slot3   slot4   slot5
R1    elysia  hono    bun     effect  express
R2    hono    bun     effect  express elysia
R3    bun     effect  express elysia  hono
R4    effect  express elysia  hono    bun
R5    express elysia  hono    bun     effect
```

ทุก Framework ได้อยู่ทุกตำแหน่งตำแหน่งละหนึ่งครั้งพอดี ซึ่งแข็งแรงกว่าการสุ่ม: **ผลกระทบเชิงเส้นจากตำแหน่งจะถูกหักล้างออกจากค่าเฉลี่ยของแต่ละ framework โดยตัวโครงสร้างเอง** การป้องกันจึงเป็นเชิงโครงสร้าง ไม่ใช่เชิงสถิติ

เดิมผมตั้งใจจะแค่สลับหน้า-หลังกลับไปกลับมาในแต่ละรอบ

แต่กับห้า Framework วิธีนั้นใช้ไม่ได้ — การกลับลำดับรายการห้าตัวทำให้ตัวกลางอยู่ที่ตำแหน่ง 3 ทุกครั้ง ตัวที่เราอยากขยับที่สุดกลับไม่เคยขยับเลย

### ช่วงพักที่เป็น baseline ไปในตัว

พัก 120 วินาทีระหว่างทุกการวัด บวก pre-roll และ post-roll อีกอย่างละ 120 วินาที ได้ **26 ช่วง idle มาฟรี ๆ** ผม integrate 60 วินาทีท้ายของแต่ละช่วง (หักขอบข้างละ 2 วินาที) ซึ่งข้ามช่วง teardown เซิร์ฟเวอร์ การเขียน page cache กลับ และการไล่ DVFS ลง

นี่คือ idle แบบ *อุ่น* ไม่ใช่แบบเย็น กระแสรั่วในซิลิคอนสูงขึ้นตามอุณหภูมิ ค่า idle หลังผ่านไปหนึ่งชั่วโมงจึงควรสูงกว่าที่นาทีที่ห้า การลบพื้นแบบอุ่นออกคือทางเลือกที่อนุรักษนิยมกว่า

### ไม่แก้โค้ด benchmark

Suite ที่ใช้คือ [bun-http-framework-benchmark ของ SaltyAom](https://github.com/saltyaom/bun-http-framework-benchmark) ปักที่ `383eddd` ตัว `bench.ts` ครอบ entry point ด้วย `if (import.meta.main)` และ **export** `startServer`, `waitForStartup`, `validateServer`, `ensurePortFree` กับ `buildBenchmarkArgs` ออกมา runner ของผมจึง import ของพวกนั้นมาขับ benchmark ผ่านเส้นทางโค้ดของ upstream เองโดยไม่แก้แม้แต่บรรทัดเดียว — `git status --porcelain` บน clone แสดงแค่โฟลเดอร์ `energy/` ที่ผมเพิ่มเข้าไป

นี่ไม่ใช่ความละเอียดเพื่อความละเอียด เพราะ `buildBenchmarkArgs` เป็นฟังก์ชันของ upstream เอง บรรทัดคำสั่ง bombardier จึงเป็นของ upstream โดยโครงสร้าง และ runner ยืนยันมันทีละตัวอักษรก่อนจะใช้เวลา 75 นาที นอกจากนี้ `main()` ของ upstream ไม่เคยถูกเรียก ซึ่งบังเอิญทำให้กับดักสองข้อจากโพสต์ก่อนหายไปเอง: `results/` ไม่เคยถูกลบ และ `results.md` ไม่เคยถูกเขียน

สี่จุดที่ผม *เปลี่ยน* จริง และเปิดเผยทั้งหมด:

1. bombardier ได้ `-p r -o json` เพิ่ม — ไม่มีแถบความคืบหน้า ผลลัพธ์อ่านด้วยเครื่องได้ ทำงาน *น้อยกว่า* ค่าเริ่มต้นของ upstream ด้วยซ้ำ
2. เว้น 2 วินาทีคงที่ระหว่าง route เพื่อให้หน้าต่างพลังงานแยกกันสะอาด upstream รันติดกัน
3. build framework ครั้งเดียวตั้งแต่ต้น พลังงานของ `Bun.build` จึงอยู่นอกทุกหน้าต่างที่วัด
4. งานทั้งหมดรันใต้ `caffeinate -dimsu` เครื่องนี้ตั้งเวลาหลับตอนเสียบไฟไว้ที่หนึ่งนาที และโปรเจกต์ก่อนหน้าเคยเสียการรันทั้งรอบไปกับเรื่องนี้พอดี

## แล้วจูลพวกนั้นไปไหน?

bombardier รันบนสิบคอร์เดียวกับเซิร์ฟเวอร์ที่มันกำลังวัด ผมจึงรันอีกรอบแยกด้วย sampler `tasks` ของ powermetrics เพื่อดูว่าพลังงานเป็นของตัวยิงโหลดเท่าไร

**ผมคำนวณการแบ่งจูลรายโปรเซสไม่ได้ และความล้มเหลวนั้นน่าสนใจกว่าตัวเลขที่ควรจะได้**

ผม fit `joules = a·P_core_seconds + b·E_core_seconds` ข้ามหน้าต่างทั้งหมด ผลออกมาได้ **สัมประสิทธิ์ของ E-core เป็นลบ** — ซึ่งแปลว่าการรันงานบนคอร์ประหยัดพลังงาน *ปล่อย* พลังงานออกมา — พร้อม R² เพียง 0.48 โมเดลนี้ผิด และผิดด้วยเหตุผลเชิงกายภาพ ลองเทียบสองหน้าต่าง:

| | เวลา P-core | เวลา E-core | พลังงาน |
| --- | ---: | ---: | ---: |
| elysia / ping | 51,944 ms | 43,693 ms | 168.5 J |
| express / ping | 27,957 ms | 1,146 ms | 148.3 J |

Elysia สะสมเวลา P-core 1.9 เท่า และเวลา E-core 38 เท่า เพื่อพลังงาน 1.14 เท่า ที่สภาวะอิ่มตัว **กำลังไฟรวมของ SoC แทบไม่ขึ้นกับว่าคุณสะสมเวลา CPU ไปเท่าไร** เครื่องอยู่ใกล้เพดานกำลังไฟอยู่แล้ว และคอร์ก็เข้าไปเติมช่องว่างรอบ ๆ พลังงานจึงไม่ได้แปรผันตรงกับเวลา CPU และแบ่งตามสัดส่วนเวลา CPU ไม่ได้

การอ่านค่า "0.0958 mJ ต่อ request" อย่างซื่อสัตย์จึงเป็น: นั่นคือสิ่งที่ *เครื่องนี้* ใช้ไปต่อ request ขณะกำลัง benchmark ตัวเอง และ framework ที่กำลังทดสอบเป็นเพียงส่วนน้อยของมัน มันเป็นตัวเลขที่ใช้เทียบ framework กันเองภายใต้เงื่อนไขเดียวกันได้ แต่ไม่ใช่ต้นทุนของการเสิร์ฟ request จริงบน production และไม่ใช่ 0.0958 mJ ของ Elysia

- **17–38% ของเวลา CPU ในหน้าต่างระบุที่มาไม่ได้** `DEAD_TASKS` คือถังของ powermetrics สำหรับโปรเซสที่จบไปกลาง sample มันแปรผันตาม framework ที่ทดสอบ ไม่ได้เป็นพื้นหลังคงที่ ผมจึงแยกมันออกมาให้เห็นชัด แทนที่จะยัดรวมใน "อื่น ๆ" ทุกสัดส่วนข้างบนควรอ่านเป็นขอบเขต ไม่ใช่ค่าจุดเดียว
- powermetrics ยังมี `--show-process-energy` ซึ่งคือค่า "Energy Impact" ของ Activity Monitor — ค่าประกอบที่ไม่มีหน่วยและไม่เปิดเผยสูตรถ่วงน้ำหนัก มันไม่ใช่จูล และผมไม่ได้ใช้มันคำนวณอะไรเลย

ราบเรียบภายใน 0.07% ถ้าหาสหสัมพันธ์กับนาทีในเซสชันแทน ได้ **r = −0.018**

มีความซื่อสัตย์เชิงสถิติข้อหนึ่งที่โพสต์ก่อนข้ามไป: ที่ n = 75 ค่าความคลาดเคลื่อนมาตรฐานของ r อยู่ราว 0.118 ดังนั้นอะไรที่ต่ำกว่า |r| ≈ 0.23 ถือว่า *สอดคล้องกับศูนย์* ไม่ใช่ *พิสูจน์ว่าไม่มี* ค่า r = 0.03 ของผมผ่านเกณฑ์นั้นสบาย ๆ แต่ "สอดคล้องกับศูนย์" คือข้ออ้างที่ถูกต้อง ส่วน r = +0.09 ที่ n = 40 ของโพสต์ก่อนก็สอดคล้องกับศูนย์เช่นกัน ไม่ใช่ข้อพิสูจน์

และ Latin square ทำงานหนักในเชิงโครงสร้าง ไม่ใช่เชิงสถิติ — ผลกระทบเชิงเส้นจากตำแหน่งถูกหักล้างโดยตัวการออกแบบเอง ค่าสหสัมพันธ์เป็นแค่การตรวจหา drift *ที่เหลือ* ซึ่งไม่เป็นเชิงเส้น

## เครื่องลดความเร็วเพราะความร้อนไหม?

ไม่ และคราวนี้ผมแสดงให้ดูได้ ไม่ใช่แค่กล่าวอ้าง

กำลังไฟขณะ idle ไปจาก **26 mW ที่นาทีที่ 0 เป็น 21 mW ที่นาทีที่ 69** ความชันที่ fit ได้คือ +0.0002 W ต่อชั่วโมง ราบเรียบ ค่า `thermal_pressure` อ่านได้ `Nominal` ครบทั้ง 100 หน้าต่างที่วัด และ S-cluster อยู่ราว 4.2 GHz ตลอด

นั่นเป็นผลที่ต่างจากโพสต์ก่อนอย่างชัดเจน ซึ่ง throughput ลดลง 15% ภายในการรันไล่กันรอบเดียว ความต่างคือช่วงพัก 120 วินาที การวัด 25 ครั้งแบบยิงสั้น 10 วินาทีคั่นด้วยการพักสองนาที ไม่เคยสะสมภาระความร้อนแบบที่การรันต่อเนื่องห้านาทีทำได้

หมายเหตุเชิงวิธีการสำหรับคนที่จะทำตาม เดิมผมวางแผนใช้ `--show-plimits` เพื่ออ่านค่าจำกัดความเร็ว CPU โดยตรง **แต่มันไม่เพิ่ม key ใด ๆ ใน output แบบ plist บน macOS 26.6.2** มันมีผลเฉพาะรูปแบบข้อความที่มนุษย์อ่าน ไม่มีฟิลด์ speed-limit หรือ forced-idle ให้ parse หลักฐานเรื่องการลดความเร็วในโพสต์นี้จึงมาจากความถี่ต่อ cluster, `thermal_pressure` และเส้น idle-drift ข้างบน

และเช่นเคย `pmset -g therm` ไม่รายงานอะไรเลยตั้งแต่ต้นจนจบ บนเครื่องนี้มันยังใช้เป็นสัญญาณเรื่อง throttling ไม่ได้

## ปัญหาที่เจอระหว่างวัด

ความคลาดเคลื่อนที่ใหญ่ที่สุดที่ผมเจอ ไม่เกี่ยวกับความร้อนเลย

**ฟิลด์ `timestamp` ของ powermetrics มีความละเอียดแค่ระดับวินาที** sample ที่ติดกันใช้ timestamp เดียวกัน แล้วกระโดดทีละ 1000 ms ขณะที่ `elapsed_ns` ใน sample เดียวกันละเอียดถึงเศษเสี้ยวมิลลิวินาที ถ้าคุณจัดตำแหน่งหน้าต่างโหลด 10 วินาทีกับนาฬิกาความละเอียดหนึ่งวินาทีนั้น — ซึ่งเป็นสิ่งที่ทุกคนจะทำ — คุณอาจใส่กำลังไฟผิดเข้าไปในทุกหน้าต่างได้ถึงหนึ่งวินาที

การแก้เรื่องนี้ทำให้ค่าวัตต์เฉลี่ยขยับราว 4% และทำให้ coverage ของหน้าต่างจาก 1.009 กลายเป็น 1.000 พอดี วิธีแก้คือสร้างแกนเวลาที่แม่นยำขึ้นใหม่จาก `elapsed_ns` สะสม แล้วยึดกับ timestamp หยาบ ๆ ด้วยกำลังสองน้อยสุด บวก 500 ms เพื่อชดเชย bias จากการตัดเศษ

อีกสองเรื่องเล็กกว่า เผื่อช่วยใครประหยัดเวลาไปครึ่งวัน:

- macOS 26 ตั้งชื่อ cluster ประสิทธิภาพสูงว่า **`S-Cluster`** ("Super") ไม่ใช่ `P-Cluster` โค้ดที่มองหา `P` จะไม่เจออะไรเลยแบบเงียบ ๆ
- bombardier ให้ percentile ของ `rps` แต่ไม่ให้ของ `latency` — percentile ของ latency ต้องใช้ `-l` ซึ่ง upstream ไม่ได้ส่ง

## สิ่งที่ผมอยากเตือน

- **นี่คือเครื่องเดียว ห้องเดียว บ่ายเดียว** การวัด 25 ครั้งบอกได้แค่ระดับ noise ของโน้ตบุ๊ก *เครื่องนี้* และไม่บอกอะไรเลยเกี่ยวกับ M5 เครื่องอื่นหรือเครื่องที่มีพัดลม
- **ตัวยิงโหลดอยู่ในทุกตัวเลข** และสำหรับ framework ที่เร็ว มันเป็นส่วนใหญ่ของเวลา CPU ด้วยซ้ำ ดูหัวข้อการแบ่งส่วน
- **พลังงานเป็นของ SoC เท่านั้น** ไม่มี DRAM ไม่มีจอ ไม่มี SSD ไม่มีอะไรที่ปลั๊ก
- **สำหรับสี่ตัวที่เร็ว นี่เกือบเป็นการเล่าเรื่อง throughput ซ้ำ** ค่าวัตต์ของพวกมันห่างกันไม่ถึง 1% ดังนั้น mJ/request ≈ วัตต์ ÷ rps โดยที่วัตต์แทบคงที่ การถดถอยระหว่างสองค่านี้ให้ r² = 0.971 ข้อมูลที่เป็นอิสระจริง ๆ อยู่ที่ Express และที่คอลัมน์ video ไม่ใช่ในกลุ่มที่เร็ว
- **สามในห้าตัวเป็น pre-release** — Elysia 2.0.0-beta.4, Effect 4.0.0-beta.102 — ตัวเลขเหล่านี้คือภาพนิ่งของเป้าหมายที่กำลังเคลื่อนที่
- **handler ของ benchmark ว่างเปล่า** ทันทีที่ handler ต้อง await ฐานข้อมูล ทุกอย่างในนี้จะเล็กลงจนแทบไม่สำคัญเมื่อเทียบกับ query
- **ตัว sampler เองก็มีต้นทุน** การรัน powermetrics ที่ 2 Hz ทำให้ throughput ลดราว 1.5–2.7% เมื่อเทียบ A/B กับการรันที่ไม่มีเครื่องมือวัด มันเท่ากันทุก framework จึงหักล้างกันเวลาเปรียบเทียบ แต่ตัวเลขสัมบูรณ์สูงเกินจริงอยู่เล็กน้อย

และขอย้ำการเปิดเผยเหมือนคราวก่อน: ผมเคยมีส่วนร่วมกับเอกสารของ Elysia และ Elysia ก็มาเป็นอันดับหนึ่งในตารางนี้อีกครั้ง
